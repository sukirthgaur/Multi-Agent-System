# Multi-Agent Research Assistant — Architecture & Design Writeup

## 1. System Architecture

The research assistant is designed as a multi-agent orchestration hierarchy using the **Google Gemini API** (`@google/generative-ai`) and free web search tools.

```
                        +----------------------+
                        |     Coordinator      |
                        | (Gemini Main Agent)  |
                        +----------+-----------+
                                   |
             +---------------------+---------------------+
             |                                           |
             v                                           v
  +----------------------+                    +--------------------+
  |    web-researcher    |                    |     summarizer     |
  |   (Gemini + Free     |                    | (Gemini + Zero     |
  |  DuckDuckGo Search)  |                    |      Tools)        |
  +----------------------+                    +--------------------+
```

### Agent Roles & Specifications

1. **Coordinator (Main Agent)**
   - **Responsibility**: Analyzes the root prompt, decomposes the user's question into independent sub-questions, delegates tasks to researchers in parallel, and passes collected context to the summarizer.
   - **Model**: `gemini-1.5-flash` (Google Gemini API).

2. **Web Researcher (`web-researcher`)**
   - **Responsibility**: Executes targeted research for a single sub-question using free web searches (DuckDuckGo search scraper).
   - **Inputs**: One sub-question.
   - **Outputs**: Concise bullet points paired with URL source citations.
   - **Tools Allowed**: `["WebSearch"]` (strictly isolated fact gathering).

3. **Summarizer (`summarizer`)**
   - **Responsibility**: Aggregates disparate research reports into a cohesive, structured final document.
   - **Inputs**: Combined research findings and explicit notes on any unfulfilled queries.
   - **Outputs**: Consolidated narrative with inline citations and identified knowledge gaps.
   - **Tools Allowed**: `[]` (pure text synthesis; zero tool access).

---

## 2. Orchestration Decisions

### Delegation & Prompting
Orchestration relies on Gemini API model declarations, function calling, and structured prompt metadata:
- **Parallel Execution**: Sub-questions generated by the coordinator are executed concurrently via `Promise.all`, running subagents in parallel to optimize overall latency.
- **Context Isolation**: Each researcher operates in a fresh model session. Intermediate search queries and snippets do not bloat the main coordinator's context window.

---

## 3. Error Handling & Resilience Strategy

### Skip-with-a-Note Pattern
In real-world web research, individual search queries may fail due to rate limits, connection drops, or unindexed topics.
- The coordinator prompt explicitly enforces resilience: if a subagent returns empty results or encounters an error, the coordinator continues processing remaining sub-questions and explicitly instructs the summarizer to note the missing data.

### Search Failure Injection Hook
To demonstrate failure handling deterministically without relying on live network outages:
- A `searchFailureHook` intercepts `WebSearch` tool calls prior to execution.
- When `SIMULATE_SEARCH_FAILURE=true`, the hook intercepts the request and returns `{ allowed: false, reason: "Simulated failure for demo purposes" }`.
- This exercises the system's ability to gracefully downgrade performance while keeping the overall orchestration loop intact.
